# AI Crew · 多 Agent 群聊协作平台

几个具名 Agent 待在一个群聊里,你丢一个目标进去,它们轮流发言、互相 @、商量出结论,然后散会。

不是"把一个任务拆成流水线",而是**让它们像同事一样开会** —— 每个 Agent 发言前都能看到群里此前的全部对话,所以后说的会回应先说的。

```
你:下个月要上线一个算命网站,先把活分了

Dev:   ⏱ 我这边先揽后端。@Mochi 你别又说我方案脆,这次给你留了扩展位。
Mochi: 🍡 后端没问题,但你说"留扩展位"具体是啥?没定义就等于没有。
阿策:  📐 定一下:Dev 出接口文档(周三),Mochi 照着文档挑一遍(周四)。散会。
```

## 跑起来

```bash
pip install fastapi uvicorn requests
cp config.example.py config.py     # 然后把 API_KEY 改成你自己的
py server.py
```

打开 http://127.0.0.1:5195

## 三个设计点

**1. 调度:轮次驱动,不是并发**

看到"所有人都在回复"的群聊,很容易想当然用并发。但并发下每个 Agent 看不到本轮别人说了什么,结果就是各说各话、没人接话。

这里改成顺序轮转:一轮之内依次发言,每个人发言时都拿得到截至此刻的完整聊天记录。慢一点,但"商量"是真的。

**2. 终止条件(这类系统最大的坑)**

Agent 之间自由对话**不会自己停**。不设闸门,两个 Agent 能客客气气地聊到天亮,而每一轮都是真实的 API 花费。

两道闸门:
- **硬上限**(代码层):`MAX_ROUNDS`,到点无条件散会,不依赖模型自觉
- **软自主**:提示词里约定"达成一致就在末尾加 `[散会]`",让模型也能提前收

只做第二道等于没做 —— 模型的"自觉"是请求,不是保证。

**3. 实时推送:SSE + 消息编号去重**

前端用 `EventSource` 接 `/stream`,服务端每产生一条消息就推一条。

坑在**重连**:SSE 断线会自动重连,而重连时服务端会把历史整个重放一遍 —— 前端不去重就会看到满屏重复。所以服务端给每条消息编号(`Hub.push` 里 `id = len(history)`),前端拿 `Set` 记已渲染的 id。

## 结构

```
server.py    后端:群聊状态 + 调度 + 路由(单文件)
index.html   前端:群聊界面(零构建,原生 JS)
config.py    密钥 / 端口 / 群规 / 群成员(不进仓库)
```

`server.py` 里的核心是一个 `Hub`:一份消息历史 + 每个打开网页的客户端一个队列。消息先落历史再广播,新连上来的客户端能立刻拿到完整上下文。

## 能改的地方

改 `config.py` 的 `AGENTS` 就能换人 —— 名字、头像、人设都在这儿。加第四个、给它们换成"产品 / 测试 / 运维"都行。

`MAX_ROUNDS` 是花钱的总闸门,别设太大。
